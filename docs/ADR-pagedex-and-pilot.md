# Architecture Decisions — NCERT Pagedex, Grounding & Pilot Hardening

> Companion to [ARCHITECTURE.md](./ARCHITECTURE.md) (product vision + high-level
> architecture). This document records the **decisions** behind the work that turns
> the platform from a demo into a pilot-ready, NCERT-grounded learning loop:
> the **interactive mind map**, the **NCERT "Pagedex"** (vectorless structured
> retrieval), the **capture → grounding** rewire, **eager downstream generation**,
> and **multi-tenant isolation**.
>
> Format: each decision is an ADR — Context → Decision → Rationale → Consequences.

---

## 0. System at a glance

A teacher records a class; the audio is transcribed; a structured **summary** is
generated, grounded in the **exact NCERT section the teacher taught**; from that
summary we derive a **mind map**, a **quiz**, and (on demand) a **story**. Students
consume these per class.

```
Teacher picks class/chapter/topic (canonical NCERT ids) ──▶ records audio
        │
        ▼ (Azure Blob + transcription-queue)
Transcription microservice ──▶ daily_transcripts ──▶ summary-ready queue
        │
        ▼ (summary worker)
summarize_daily_from_transcript:
   • back-fill canonical chapter/topic ids  (capture_meta sidecar)   [ADR-005]
   • NCERT grounding scoped to the taught section  (pagedex)         [ADR-002/006]
   • stamp summary_blocks into classes_daily
   • EAGER: generate mindmap + quiz                                  [ADR-007]
        │
        ▼
Student app  ──GET /classes/daily──▶  Summary · Mind Map · Story · Quiz
```

Two LLM-free guarantees underpin the design:
- **Ingestion** (PDF → content nodes) is deterministic — no model in the hot path.
- **Retrieval** (taught topic → NCERT content) is an exact id match — no model in the hot path.

The only LLMs are in *generation* (summary / mindmap / quiz / story) and an
optional *fallback* topic-resolver for the audio path that lacks a tagged topic.

## ADR-001 — Mind map as an interactive taxonomy

**Status:** Implemented.

**Context.** The student Summary tab rendered `summary_blocks` as a vertical stack
of "heavy" cards plus a flat "Words from today's class" terms grid. For a K-12
student that is high working-memory load, and a flat term list doesn't show how the
ideas relate.

**Decision.** Replace the "Words from today's class" grid with a **NotebookLM-style
interactive mind map** — a hierarchy `topic → category branches → terms (leaves)`,
with sub-leaves where one idea contains others (e.g. *Filtration → Residue,
Filtrate*). The tree is **generated by an LLM** from the class's own
`summary_blocks` and rendered with **React Flow** (`@xyflow/react`).

- Rendering: tidy left-to-right tree, **progressive disclosure** (branches collapsed
  → tap to expand), **tap a leaf for its one-line meaning**, plus **Download (PNG)**
  and **Full window**.
- Generation: lazy + cached on first view, then **eager** (see ADR-007). Cached on
  `classes_daily.mindmap`.

**Rationale.** A mind map is an *advance organizer*: show the topic's shape first,
then let the student pull detail one node at a time (segmenting), which is exactly
what protects working memory. Generating from `summary_blocks` (not the transcript)
keeps the map consistent with what the student already sees and is a cheap, focused
prompt; leaf notes reuse the real term meanings (no hallucinated definitions).

**Consequences.**
- New deps `@xyflow/react` + `html-to-image` (React 19 compatible).
- Backend `generate_mindmap()` is deliberately *source-agnostic*: it consumes
  `summary_blocks` today; the renderer only consumes `{root, branches}`.
- Files: FE `SummaryMindMap.jsx`, `MindmapService.js`, `SummaryRenderer.jsx`;
  BE `app/services/mindmap.py`, `POST /api/classes/daily/mindmap`.

## ADR-002 — NCERT "Pagedex": vectorless structured retrieval

**Status:** Implemented (first chapter proven end-to-end).

**Context.** NCERT content grounds summaries/stories/quizzes, but was stored and
retrieved **page-level and whole-chapter** (`resolve_ncert_content()` returned the
entire chapter text capped at 6000 chars, with no topic filtering).

**Decision.** Model NCERT as a **content graph ("Pagedex")** — a new `ncert_nodes`
collection of typed nodes (`text` / `table` / `figure` / `exercise`), each tagged
with `chapter → topic → subtopic` + page + reading order. **Retrieval is a metadata
filter, not vector search.**

**Rationale.** NCERT is a tiny, finite, rigidly-structured corpus (~600 chapters
across classes 3–12). The retrieval need is "give me the content for *this*
chapter/topic," not fuzzy semantic search. Embeddings would add a vector index,
cost, latency and non-determinism for ~zero benefit. A deterministic map is also
**auditable** ("verified against NCERT, p.84, Fig 5.6") — which is exactly the trust
the UI advertises.

**Scale.** ~600 chapters → ~9k pages, ~5k figures, ~15k nodes. Trivial for Mongo;
metadata filters on indexed fields are sub-millisecond. No sharding, no vectors.

**Consequences.**
- New package `app/services/ncert/`: `structure.py`, `nodes.py`, `pipeline.py`,
  `retrieval.py`, `blob.py`.
- New collection `ncert_nodes`; `curriculum_chapters` gains a `toc` tree + `status`.
- The existing `cbse_docs` vector path (`services/rag.py`) is **kept only where it's
  already used** (open-ended quiz search) — never for NCERT grounding.

## ADR-003 — Deterministic page-range section assignment

**Status:** Implemented.

**Context.** The hard part of the Pagedex is *segmentation*: deciding which subtopic
each extracted block belongs to. NCERT PDFs have no machine-readable link from a
subtopic heading to its content span, and the curriculum data had **no page ranges**.

**Decision.** **Auto-detect the real NCERT section headings** from the PDF — they
are numbered (`5.1`, `5.3.2`) and set in a larger bold font, so the hierarchy is
*encoded in the numbering* and detectable deterministically. Build a TOC with page
ranges, then assign each content node to a section by **page-range lookup**:
`node.subtopic = the section whose [page_start, page_end] contains node.page`.

```
5.1 How Can We Classify Mixtures?              p.2
5.2 Solutions                                  p.3   → 5.2.1 / 5.2.2 / 5.2.3
5.3 Methods of Separation (Homogeneous)        p.6   → 5.3.1 Crystallization …
5.4 How Can We Separate (Heterogeneous)        p.12  → 5.4.1 … 5.4.4
5.5 Tyndall Effect                             p.16
```

**Rationale.** Arithmetic, fully auditable, **no LLM and no hallucination surface**
at ingestion. (An earlier draft proposed an LLM to assign blocks to sections; that
was rejected once we confirmed numbered headings give exact page ranges. The only
edge case — two sections sharing one page — is handled by a within-page heading
split, still deterministic.)

**Consequences.**
- The **real NCERT sections become the canonical topics** (see ADR-005), replacing
  the LLM-generated `concepts` as the retrieval key.
- Extraction reuses the proven PyMuPDF extractor in `ncert_ingest_service._extract`;
  heading detection + TOC live in `ncert/structure.py`.
- CLI: `python -m app.scripts.ingest_ncert --pdf … --chapter-key science_class9_ch05 …`

## ADR-004 — Figures in Azure Blob, not base64 in Mongo

**Status:** Implemented for the Pagedex path; legacy `ncert_figures` migration is a fast-follow.

**Context.** Figures were stored as base64 data-URIs inline in Mongo
(`ncert_figures.image_b64`). On Cosmos that bloats documents, costs RUs on every
read (the catalog endpoint already had to project the field out), and adds ~33% size
overhead.

**Decision.** Store figure **binaries in Azure Blob** at a deterministic key and keep
only `{blob_key, width, height, caption, figure_number}` in the node. Serve via a
short-lived **SAS URL**. Reuses the existing Azure Storage account/credentials
(`AZURE_STORAGE_CONNECTION_STRING`) and the audio-upload Blob pattern.

```
blob_key = ncert/{class}/{subject}/{chapter_key}/{figure_id}.png
```

**Consequences.**
- New settings `NCERT_BLOB_CONTAINER` (default `ncert`), `NCERT_FIGURE_SAS_TTL_MIN`.
- `ncert/blob.py` — `upload_figure_png`, `figure_url`. Falls back to in-node base64
  only when Blob is unconfigured (local dev).
- Legacy `ncert_figures` (base64) and the `/ncert/figure/{id}` story path are
  **not yet migrated** — fast-follow.

## ADR-005 — Canonical topic ids as the retrieval key + capture_meta sidecar

**Status:** Implemented.

**Context.** For retrieval to scope precisely, the teacher's selected chapter/topic
must reach generation as **canonical ids**. The frontend selectors already emit them
(`chapter_unique_id`, `topic_unique_id` from `/ncert/topics`, sourced from our own
curriculum). But on the audio path those ids were **dropped**: only a title survives
in the blob filename, the transcription microservice rebuilds the transcript from
that filename, and the summary worker then **LLM-guessed** the topic.

**Decision.** Two parts:
1. **Canonical ids are the retrieval key.** `/ncert/topics` now surfaces the real
   NCERT TOC sections as topics, with `topic_unique_id = f"{chapter_key}::{number}"`
   (e.g. `science_class9_ch05::5.3`). The Pagedex keys on these exact ids, so a
   teacher's selection joins by exact match — **no model on the hot path.**
2. **`capture_meta` sidecar.** At audio-upload time the backend stashes the canonical
   `{chapter_key, topic_ids}` in a `capture_meta` doc keyed by the class identity the
   summary flow already resolves on — `(tenant, class_no, section, subject)`. The
   summary flow reads it back and stamps `chapter_key` / `topic_ids` onto
   `classes_daily`.

**Rationale.** This carries the canonical ids end-to-end **without touching the blob
filename scheme or the separate transcription microservice** (the riskiest, least
testable surface). The join key is the natural class identity, not a fragile
reconstruction of the transcript id from a filename.

**Consequences.**
- New collection `capture_meta`; `DailyClass` gains `chapter_key` + `topic_ids`.
- Files: `services/capture_meta.py`, `routers/audio_upload.py`,
  `services/summary_blocks.py`.
- The LLM topic-resolver remains **only as a fallback** for the audio-only path with
  no tagged topic, and for optional subtopic narrowing.

## ADR-006 — Section-scoped grounding with safe fallback

**Status:** Implemented.

**Context.** Summary (and later story) generation needs NCERT grounding scoped to
the taught section, but must never *mis-scope* on a vague topic string.

**Decision.** `resolve_grounding(class_no, subject, chapter_key, topics, topic_ids)`
returns `{content, chapter_key, figures, scope}` where `scope ∈ {section, chapter,
concepts}`:
- **Canonical `topic_ids`** (exact id) win → `section` scope (that section's text +
  figures only).
- Else a **conservative** match on `topics` (exact section name / number) → `section`.
- A vague topic (e.g. the chapter title) or no match → **whole-chapter fallback**
  (`chapter`), then the curriculum concept snippet (`concepts`). Never a wrong scope.

**Rationale.** Forward-compatible: scoping "lights up" automatically the moment a
daily stores a canonical section id, while today's demo data (topic = chapter title)
safely grounds to the whole chapter — **no regression**.

**Consequences.**
- `ncert/retrieval.py` `resolve_grounding`; wired into
  `summarize_daily_from_transcript` and the `test-summary` regenerate path. Legacy
  `resolve_ncert_content` kept working.
- Verified: `topic_ids=["…::5.3.2"]` → section scope, 4.2k chars + Figs 5.11–5.14;
  `topics=["Separation of Mixtures"]` (chapter title) → chapter scope (no mis-scope).

## ADR-007 — Eager downstream generation

**Status:** Implemented.

**Context.** The summary worker produced `summary_blocks` but did **not** trigger
quiz generation (it could 404), and mindmap/story were lazy (built only when a
student opened the tab).

**Decision.** After the summary is stamped, `summarize_daily_from_transcript` runs
`_eager_downstream()` — generates the **mindmap** and **quiz** immediately,
best-effort (each independent; a failure never breaks the summary). This runs in the
shared flow, so it fires for both the **production summary worker** and the API.

**Rationale.** Students should never open an empty/404 tab. Quiz + mindmap are
class-level (not per-student) so eager generation is safe and cheap. **Story stays
lazy** — it's per-student (`student_id`) and correctly built on tab open.

**Consequences.** `_eager_downstream` in `services/summary_blocks.py`; logs
`[EAGER] mindmap ready` / `[EAGER] quiz ready`.

## ADR-008 — Ingestion as a separable-in-backend module

**Status:** Implemented (module + CLI); standalone worker is a future lift.

**Context.** PDF ingestion (parse + structure) is CPU-heavy, bursty and
admin-triggered — it should not sit in the API request path. But a full microservice
is premature at current scale.

**Decision.** Build ingestion as a **self-contained, queue-ready, idempotent module**
(`app/services/ncert/`) that communicates only via shared Mongo + Blob + Queue with
stable ids — runnable today as a CLI, liftable later into a standalone
`ncert-ingest` worker (the transcription-service template: Azure Container Apps +
KEDA) with **no rewrite**. **Retrieval stays in-process** (just a Mongo filter +
Blob URL signing).

**Rationale.** "Modular monolith → extractable service." Decoupling rules (Mongo/Blob/
Queue only, stable deterministic ids, a versioned node schema) make the future split
mechanical instead of a rewrite.

## ADR-009 — Multi-tenant isolation + ENV-aware hardening

**Status:** Implemented (data-plane); real per-user auth + onboarding are separate, larger workstreams.

**Context.** A pilot puts a *real school* on the platform. Audit found per-student /
per-class data being read **without a tenant filter** across many endpoints, a
hardcoded `tenant="demo-school"` in teacher insights, dev placeholders for secrets,
and a `?demo=` flag that bypasses date filtering.

**Decision.**
- **Tenant on every per-tenant query.** Systematic sweep: every read/write of a
  per-tenant collection (`students`, `classes_daily`, `quizzes`,
  `student_quiz_attempts`, `student_daily_progress`, `story/guru/silf/comic`,
  `student_interventions`, `streak_tracking`, `quiz_responses`, `capture_meta`, lesson
  plans) now filters by `tenant`. Global collections (`curriculum_chapters`,
  `ncert_*`, `cbse_docs`) are intentionally **not** scoped.
- **ENV-aware enforcement.** `get_tenant` **requires** `X-Tenant-ID` in
  staging/prod (no `demo-school` fallback) but keeps the dev default so the demo
  works. `settings.assert_production_ready()` **fails fast at startup** in prod when
  critical secrets are empty or still dev placeholders. `?demo=` date-bypass is
  ignored in prod.

**Rationale.** Defense by consistent filtering at the data layer; hard in prod,
unchanged in dev. Existing demo docs all carry `tenant: "demo-school"`, so the sweep
doesn't break the demo.

**Consequences.**
- Touched routers: `students`, `classes`, `daily_quiz`, `quiz`, `quizzes`,
  `question`, `intervention`, `admin`, `leaderboard`, `progress`, `ai`,
  `teacher/{quiz,insights,interventions,lesson_plan}`; service
  `teacher/lesson_plan` threaded with tenant. Also fixed a latent bug in legacy
  `quizzes.py` (`{"$oid": …}` was never a valid Mongo query).
- **Intentionally left** (documented): `transcripts` / `simulations` fetched by
  `daily_id` (the daily is tenant-gated in the same handler, and those docs aren't
  guaranteed to carry `tenant`); `GET /compare` (internal eval / DEMO).
- **Not in scope** (flagged as pilot blockers you own): rotating the secrets
  committed in `populate_mock_data.py`, real per-user auth (currently a static
  `dev-local-key` + mock login), and an onboarding/roster flow.
- Regression watch: a legacy doc **missing** a `tenant` field will now be filtered
  out (404 / regenerate). Fix is a one-line backfill of `tenant` on that collection.

## Data model reference

Per-tenant collections carry a `tenant` field. **Bold** = added/changed by this work.

| Collection | Scope | Key fields |
|---|---|---|
| `classes_daily` | per-tenant | `tenant, date, class_no, section, subject, topics[], `**`chapter_key, topic_ids[]`**`, summary_blocks[], `**`mindmap`**`, try_it_widget` |
| **`ncert_nodes`** | global | `_id, chapter_key, class, subject, type(text\|table\|figure\|…), topic, topic_id, subtopic, subtopic_id, order, page_start, page_end, text\|table\|figure, extractor_version` |
| `curriculum_chapters` | global | `chapter_key(uniq), class, subject, chapter_number, chapter_title, concepts[], `**`toc[], status, extractor_version`** |
| `ncert_chapter_text` | global | `chapter_key, page, text, tables[]` (kept for back-compat) |
| `ncert_figures` | global | legacy base64 figures (migration pending) |
| **`capture_meta`** | per-tenant | `tenant, class_no, section, subject (uniq), chapter_key, topic_ids[], topics[], updated_at` |
| `quizzes`, `student_quiz_attempts`, `student_daily_progress`, `streak_tracking`, `quiz_analytics` | per-tenant | quiz + progress + gamification |
| `story_generations`, `guru_shishya_stories`, `silf_story_generations`, `comic_stories` | per-tenant | generated stories, cached by `(daily_id, student_id[, format])` |
| `student_interventions` | per-tenant | adaptive intervention records |
| `daily_transcripts`, `transcripts` | per-tenant\* | transcripts (\*keyed by `daily_id`; see ADR-009) |

`curriculum_chapters.toc`:
```jsonc
"toc": [ { "topic_id", "number", "name", "page_start", "page_end",
           "subtopics": [ { "subtopic_id", "number", "name", "page_start", "page_end" } ] } ]
```

`ncert_nodes` (figure example):
```jsonc
{ "_id": "NCERT_SCI_9_CH05_FIG_5_11", "chapter_key": "science_class9_ch05",
  "type": "figure", "topic_id": "science_class9_ch05::5.3", "subtopic_id": "science_class9_ch05::5.3.2",
  "order": 20, "page_start": 9, "page_end": 9,
  "figure": { "blob_key": "ncert/9/Science/science_class9_ch05/NCERT_SCI_9_CH05_FIG_5_11.png",
              "width": 512, "height": 384, "caption": "Distillation set-up", "figure_number": "5.11" } }
```

## Identifier conventions

| Thing | Format | Example |
|---|---|---|
| Chapter | `chapter_key` | `science_class9_ch05` |
| Topic (TOC section) | `{chapter_key}::{number}` | `science_class9_ch05::5.3` |
| Subtopic | `{chapter_key}::{number}` | `science_class9_ch05::5.3.2` |
| Figure | `NCERT_{SUBJ}_{class}_{CHxx}_FIG_{n_m}` | `NCERT_SCI_9_CH05_FIG_5_11` |
| Text/table node | `{chapter_key}::text::{page}` / `::table::{page}::{i}` | `science_class9_ch05::text::9` |
| Daily transcript | `{schoolId}_{classId}_{subject}_{timestamp}` | `SCH-123_9A_Science_1730000000` |

**LLMs in use:** generation (summary / mindmap / quiz / story) runs on **Gemini 2.5
Flash** (`GEMINI_CHAT_MODEL`) via the OpenAI-compatible endpoint, with Azure OpenAI
as fallback. Ingestion and retrieval use **no LLM**.
